{#- THE SETTINGS LANDING PAGE — a grid of TILES, one per plugin / service. It replaces the old list of YAML filenames. The two kinds are told apart AT A GLANCE four ways at once — the 3px left rail (colour), the kind GLYPH, the kind WORD, and the scope line — never by colour alone. THE CARD MARKUP IS SHARED. The WHOLE card — shell, head, name, description, foot and switch — is NOT written here: it comes from `_tiles.html` (`tile_card`, `switch_control`, the kind glyphs, the cogwheel), the very macros the NODE page uses for its extension cards — so the two surfaces cannot drift apart. NODE AND EXTENSION CONFIGURATION ARE NOT HERE. A node's own settings and the extensions bound to it (or to one of its instances) all live in `nodes.yaml`, and the NODES page now edits them through the node page (`/nodes/`, `Node-wide` tab = the node, then one `Instance ` tab each). The old "This install → nodes.yaml" tile and the whole EXTENSIONS rail are therefore GONE — no duplicate entry point, and no `/settings/extension/` page. ON/OFF, per kind (the mechanism the bot actually uses) is computed in `pages.settings.load_landing` into each row's `switch` model; the SAME `switch_control` macro draws every one of them: * a PLUGIN is enabled by its name being in `opt_plugins` (or absent-key `plugins`); the switch posts the SAME `f.opt_plugins` list the existing plugin block writes, to the SAME save route (no new route). * a SERVICE is enabled by its config file EXISTING; the switch moves the file aside / home through the one service route, and a service held off by its PLUGIN dependency says so and moves NOTHING. Every composed word is wrapped (`_(…)`); an item's NAME and DESCRIPTION are operator data and are printed VERBATIM.
