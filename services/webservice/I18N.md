# Admin console — translating the web UI

The staff console at `/` can be served in more than one language. This page is the whole workflow:
how to extract, how to add a language, how to compile, and what a translator touches.

The migration proceeds in slices: the **login page** and the **shell** (slice 1), the
**dashboard** and the **list pages** (Servers, Nodes, Instances, Players — slice 2), the
**per-server page and its tabs** (Overview, Players, Missions, Log, Events, Configuration — slice 3),
the **write dialogs** (the one `confirm.html` component every write in the console opens — slice 4)
and the **row buttons and the console's JavaScript** (slice 5, card I5), and the top bar's
**breadcrumb** (card I7, which also wrapped its group word and reused each page's own label rather
than duplicating it) are wrapped. Every visible string in the console is wrapped — including the two
tab strips' `aria-label` attributes (`_state.html` "Cluster", `server_detail.html` "Server"), which
reuse the pages' own labels rather than adding a second msgid — so a language pack added later finds
nothing left unwrapped.
Wrapping a string is invisible until a translation exists (English is the msgid), so the tree stays
green while the work proceeds.

**What is deliberately NOT wrapped: an action's refusal and its notice.** The action's own message
(its success, its typed refusal) is composed **where the action runs** and is shown on **both** the
web console and the **Discord** side. Making it language-dependent would leak one surface's language
into the other — the same class of bug the leak test exists to catch — so it stays English here.
Translating it needs a design of its own (a translatable key carried by the notice and resolved where
it is rendered), and that design is not improvised in a slice. The **operator data** — server,
mission, player and coalition names, and the node's own name — is likewise never translated: the
console shows a translated label beside a name that stays exactly as the operator typed it.

The machinery is in [`services/webservice/i18n.py`](i18n.py); the extraction config is
[`services/webservice/babel.cfg`](babel.cfg).

## How a string becomes translatable

* In a template, wrap it with Jinja's own translation tag:
  `{% trans %}Sign in{% endtrans %}`.
* In the console's Python (`services/webservice/**/*.py`), wrap it with the `_()` marker:
  `CONTROL_LABEL = i18n._("Sign in with Discord")`. The marker returns the string unchanged — the
  real translation happens where it is rendered, by the template environment, which is built per
  language.

**English is the msgid.** A wrapped string that has no translation is a no-op: it renders exactly as
before. That is what lets the console be translated one slice at a time without any visual change
until a catalog exists.

The console keeps its **own gettext domain, `webui`**, so the frontend's strings never mix with the
bot's Discord strings (the two share almost nothing). The catalogs live in the bot's existing tree:
`locale/<lang>/LC_MESSAGES/webui.po` (source) and `webui.mo` (compiled, what runs).

## The row buttons: translate, then interpolate

A row control's tooltip and accessible name name the TARGET ("Restart server SRS-1"), and a server
name is operator data that must never be translated. So those strings are wrapped as their English
TEMPLATE (with a `{server}` / `{node}` / `{player}` hole) and rendered through the environment's ONE
guarded global `say` (`templating.SENTENCE_GLOBAL`): the template is translated FIRST, the target
interpolated AFTER. A translation that omits a hole degrades to the English sentence rather than
taking the row down (`templates/_strip.html`, `templates/_table.html`). A control's plain strings
besides its names — its menu `label`, its `hint`, a field's label/help — are rendered with the
environment's `_(…)`. The declarations in `pages/actions.py` are where a control's copy is marked.

## The console's JavaScript: a served message map

The static JS under `services/webservice/static/` carries **no user-visible string and no translation
logic**. Instead the server renders the strings for the REQUEST's language on a gated route —
`/i18n/messages.js` (`i18n.MESSAGES_PATH`, declared `dashboard.view` like the console's own pages, so
it respects the access gate exactly as they do) — as `window.DCSSB_MESSAGES` plus ONE substitution
helper, `window.dcssbMsg(key, params)`. The scripts look a key up and swap a `{name}` hole; they never
translate. `base.html` includes the map **before** the scripts that read it. The map is the SAME
`webui` catalog the pages use (its keys are `i18n.JS_MESSAGES`), so a page and its scripts can never
disagree about the language — and adding a string to the JS is adding a key there, never a JS edit.
The route is served `no-store`: a language-shaped body must never sit in a shared cache.

A JSON endpoint whose strings the JS **shows** rather than looks up needs no key at all. The SERVER
renders the sentence for the request's language and the script swaps the finished string into the DOM.
The log window (`pages/server_detail.py`) works this way: each `message` its JSON body carries is a
**sentence record** — an `i18n._`-marked English template plus its operator data — rendered through the
SAME guarded `say` the write dialogs use (`templating.SENTENCE_GLOBAL`, on the request's per-language
environment). The template is translated FIRST and the data interpolated AFTER, so a node name, a log
path or an error type stays exactly as the operator's; a bad catalog line degrades to English rather
than taking the log view down. The tab's own initial render goes through the same call, so the first
paint and every follow agree on the language. None of this lives in the JavaScript.

## Extract, update, compile

Babel is a **build/developer** tool — the console at runtime uses only the standard library's
`gettext`. It is declared as a build/test tool in `requirements.in` (`babel==2.17.0`); to run the
extraction (or the suite) on a machine without the bot's environment, install it with
`pip install babel`. Run these from the repository root:

```
# 1. pull every translatable string out of the templates and the page code
pybabel extract -F services/webservice/babel.cfg -o /tmp/webui.pot \
    --project=DCSServerBot --copyright-holder=DCSServerBot --no-wrap .

# 2. merge new/changed strings into every catalog (keeps existing translations)
pybabel update -i /tmp/webui.pot -d locale -D webui

# 3. compile the .po sources to the .mo files gettext reads
pybabel compile -d locale -D webui
```

`tests/test_webui_i18n.py::test_every_wrapped_string_is_in_the_shipped_catalogs` runs the extraction
and fails if a template or a page string is not in the catalogs — so extraction and templates cannot
drift.

## Adding a language

1. `pybabel init -i /tmp/webui.pot -d locale -D webui -l <lang>` (creates
   `locale/<lang>/LC_MESSAGES/webui.po`).
2. Translate the `msgstr` lines.
3. `pybabel compile -d locale -D webui`.
4. Add the language's own name to `LANGUAGE_NAMES` in `i18n.py` (`{"de": "Deutsch"}`) — without an
   entry it appears in the control labelled by its code — and, optionally, its flag to
   `LANGUAGE_FLAGS` (`{"de": "de.svg"}`), dropping the SVG into `services/webservice/static/flags/`
   (public-domain / MIT artwork only; see `SOURCE.txt` beside the assets). A language with no flag
   falls back to the neutral globe.

A language appears in the console's language control **as soon as its `webui.mo` exists** — the
control offers exactly the languages that can render, never an empty one. (The bot's own catalog
under `locale/de` is a **different domain** and does not make the frontend switch to that language;
the bot's catalogs sit beside the console's own `webui` catalog in the same tree, and it is the
`webui` one the frontend reads.) The list of catalogs is cached (keyed by `locale/`'s own mtime), so
compiling a NEW language is picked up without a restart.

## The language control shows flags

With more languages coming, a row of names is too long, so each option is a small **SVG flag** with
the language's own endonym kept as its `title` (tooltip) and `aria-label` (accessible name) — the
name is not drawn. English is the source language and gets a **neutral globe** rather than a national
flag. Flag EMOJI are deliberately not used: Windows renders them as the two regional-indicator
letters, so the control would look broken. The control stays plain links, so it works with
JavaScript off.

The language of a request is a code — validated and **normalised** by `normalise_language`, so an
uppercase `DE`, a `de-DE` or a `de_DE` all read as `de`.

## What a translator touches

Only the `.po` files. Never the templates, never the Python: those are the source of the msgids and
are regenerated by extraction. English (`locale/en`) is an identity catalog kept as a template to
copy.

**German is informal (Du).** This project's German catalog addresses the reader as **Du** — "Starte
den Server", "Deine Mission" — never the formal "Sie". It is not a pronoun substitution: a sentence
that only reads naturally in the formal register is rewritten into an informal one. A writer adding a
German string must match that register, and the same convention is noted in the `webui.po` header so
it survives the next extraction.

**Spanish is informal (tú).** This project's Spanish catalog addresses the reader as **tú** — "Arranca
el servidor", "Tu misión" — never the formal "usted". It is not a pronoun substitution: a sentence
that only reads naturally in the formal register is rewritten into an informal one. A writer adding a
Spanish string must match that register, and the same convention is noted in the `webui.po` header so
it survives the next extraction.

**Russian is informal (ты).** This project's Russian catalog addresses the reader as **ты** — «Запусти
сервер», «Твоя миссия» — never the formal «вы». It is not a pronoun substitution: a sentence that only
reads naturally in the formal register is rewritten into an informal one. A writer adding a Russian
string must match that register, and the same convention is noted in the `webui.po` header so it
survives the next extraction.

**Chinese is informal (你).** This project's Chinese catalog addresses the reader as **你** — 「启动
服务器」「你的任务」— never the formal 「您」. It matches the bot's own language code: the bot (its
catalogs and `main.yaml`) calls Chinese **`cn`**, not `zh`, so the console's catalog is
`locale/cn/LC_MESSAGES/webui.po` and the console and the bot agree. A writer adding a Chinese string
must use 你 and keep that code, and the same convention is noted in the `webui.po` header so it
survives the next extraction.

## The language of a request

Highest precedence first:

1. the visitor's **stored choice** — the `dcssb_lang` cookie, set by `/language`;
2. the browser's **`Accept-Language`** header;
3. the **`language:`** key in `main.yaml` (the install-wide setting, and the default).

Every value is validated against the languages that have a `webui` catalog, so an unknown or
malformed value is skipped rather than trusted. The choice is stored in its own cookie (not the
session) so it survives sign-in — the login and logout flows clear the session for session-fixation
defence, and a preference must not be lost to that.

The language is resolved **per request** and applied through a **Jinja environment per language**,
built lazily and cached — never a global `set_language`, which would leak the console's language into
the bot's Discord strings (the console runs inside the bot's own process).
